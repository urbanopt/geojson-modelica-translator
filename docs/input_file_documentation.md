# Input File Documentation

There are two key input files that need to be defined to use the GeoJSON to Modelica Translator: a GeoJSON file and
a System Parameters file.

As an aside, 5GDHC systems also require a `loop_order` JSON file, which is automatically generated by the [ThermalNetwork](https://natlabrockies.github.io/ThermalNetwork/) package and used without any human input.

## 5GDHC without a ground heat exchanger

GMT can generate a 5GDHC model when the system parameters do not include `district_system.fifth_generation.ghe_parameters`. In this topology, the generated district does not include a borefield or other ground heat exchanger plant. Instead, GMT creates an explicit no-plant boundary in the coupling graph and renders fixed-temperature heating and cooling components for the ambient loop. These components are the thermal infinite source/sink for the 5G distribution loop.

The source/sink temperature is set by `district_system.fifth_generation.no_central_plant.distribution_temperature` in degrees Celsius (`degC`) in the system parameters JSON. GMT converts this value to Kelvin (`K`) in the generated Modelica model. This value must be provided for no-GHE 5GDHC systems. It is the ideal no-central-plant distribution loop temperature, not a hidden ground heat exchanger design. The soil properties, including `district_system.fifth_generation.soil.undisturbed_temp`, remain soil/pipe heat-loss inputs and are not used as the no-plant loop temperature.

Because the no-plant source/sink is thermally ideal, GMT also adds a hydraulic pressure reference on the no-plant supply side. The generated `supNoPlant_*` `Boundary_pT` is connected to the distribution pump discharge (`pumDis.port_b`) at atmospheric pressure (`101325 Pa`) and the no-plant source/sink temperature (`K`). This boundary is only a pressure datum, analogous to an expansion or pressure-maintenance reference point. It does not add pump head (`Pa`), size the loop, or represent a physical plant. The pump, distribution network, ETS pressure drops (`Pa`), and load-derived nominal flow rates (`kg/s`) still determine hydraulic sizing and operation.

GMT reports the thermal output of the ideal no-plant source/sink with `pIdePlaHea_*` and `pIdePlaCoo_*` variables in the generated district model. Both are powers in watts (`W`) and are reported as positive values. When flow through the ideal no-plant heater/cooler is in the components' design direction, GMT uses the Buildings component heat-flow outputs. In the no-plant pressure-reference topology, flow through those ideal components can be reversed; Buildings reports `Q_flow = 0 W` in that case. GMT therefore also computes `qIdePlaRev_*` (`W`) from the reverse-flow mass flow (`kg/s`) and enthalpy difference (`J/kg`) across the ideal no-plant path. Positive `qIdePlaRev_*` is reported as cooling in `pIdePlaCoo_*`; negative `qIdePlaRev_*` is reported as heating in `pIdePlaHea_*`. These variables are thermal source/sink power, not distribution pump power.

GMT also reports `pIdePumDis_*`, an idealized distribution pump electrical power in watts (`W`) for no-plant 5G accounting. This value is computed from the actual commanded distribution-pump mass flow (`kg/s`), the fifth-generation central pump design head (`Pa`), the loop-fluid density at the no-plant reference temperature (`kg/m3`), and an ideal pump efficiency parameter `etaIdePumDis_*` (dimensionless, `0 < eta <= 1`) that defaults to `0.7`. This reported value is separate from `pumDis.P` (`W`). In the ideal no-plant hydraulic topology, the pressure references can cause the Buildings mover to see a negative machine pressure rise (`Pa`) and report zero electrical power (`W`) even while flow is circulating. `pIdePumDis_*` is therefore an accounting variable for the intended pump work, not an additional hydraulic boundary condition.

GMT does not currently calculate `district_system.fifth_generation.central_pump_parameters.pump_design_head` from the loop geometry. The `pump_design_head` value in the system parameters JSON is used directly as the distribution pump nominal head (`pumDis.dp_nominal`) and as the pressure rise (`Pa`) in `pIdePumDis_*`. The `pump_design_head_autosized` flag is therefore not a substitute for providing or reviewing this value. Use Pascals (`Pa`) and estimate the design head from the design path pressure losses, for example:

```text
pump_design_head [Pa] ~= pressure_drop_per_meter [Pa/m] * design_flow_path_length [m]
      + connection/ETS/source-side allowances [Pa]
      + design safety margin [Pa]
```

The design flow path length should represent the active distribution path at design flow, including the main one-pipe distribution segments and end segment used by the generated network (`lDis` and `lEnd`, in meters). The `pressure_drop_per_meter` input is under `district_system.fifth_generation.horizontal_piping_parameters` and is in `Pa/m`. If detailed connection or equipment pressure drops are known, include them as additional `Pa` terms. If they are not known, use a conservative engineering allowance and document the assumption. For no-plant 5G examples generated from the default template, `pump_design_head` is often initialized to `200000 Pa`, but project-specific geometry and flow can justify a different value.

For time-series loads with an internal ETS, GMT initializes the ETS service-water mixing volumes at the no-plant source/sink temperature (`K`). This keeps the ETS service side consistent with the ambient-loop thermal reference at the start of the simulation without adding artificial load (`W`), fixed flow (`kg/s`), or an implied ground heat exchanger.

For no-GHE 5GDHC systems, GMT uses a sensible-only dry cooling coil for time-series building loads by default. Other time-series systems keep the previous wet-coil cooling model by default. To opt into the dry cooling coil explicitly, set the Boolean flag `load_model_parameters.time_series.use_dry_cooling_coil` to `true` for a building in the system parameters JSON. To opt into the wet cooling coil for a no-GHE 5GDHC building, set the Boolean flag `load_model_parameters.time_series.use_wet_cooling_coil` to `true` and leave `use_dry_cooling_coil` false.

When using a hand-authored loop-order file for no-GHE 5GDHC tests or examples, GMT can read a sidecar file named after the system parameters file, such as `time_series_5g_no_plant_sys_params.json` with `time_series_5g_no_plant_loop_order.json`. This avoids conflicts with the legacy `_loop_order.json` file in the same data directory.
